# 已知问题与解决状态

本文只把尚未消除的限制列为“当前问题”。已经由代码和自动化校验覆盖的历史问题集中放在后半部分，避免给人一种所有问题仍然存在的错觉。

## 当前仍需注意

### 1. OpenOCD target cfg 必须与芯片匹配

内置 OpenOCD 包提供常见 STM32 F1/F2/F3/F4/H7 target，但不包含全部 PY32、N32 等国产 MCU 厂商脚本。cfg 文件能够加载，只代表语法可用，不代表寄存器、Flash 和复位配置一定匹配实际芯片。

当前防护：

- 常用下拉框只显示当前 OpenOCD 安装中确实存在的配置。
- 其他芯片可浏览选择厂商提供的任意 cfg。
- 自选 cfg 所在目录会加入 OpenOCD 脚本搜索路径。
- 进入工作站前会验证 executable、interface cfg 和 target cfg。

建议：PY32、N32 等型号应优先使用芯片或开发板厂商提供的 target cfg，不要用相近 STM32 cfg 猜测替代。

### 2. OpenOCD 初始化不能绝对保证不复位

OpenOCD 启动时会执行 target 初始化。是否 halt 或 reset 取决于 target cfg、探针、transport 和硬件接线，应用无法对所有芯片做绝对保证。

当前防护：配置页在 OpenOCD 日志选项下方持续显示“连接或重连 OpenOCD 可能复位 MCU”；普通 J-Link 原生连接和采样不会主动发送复位。烧录按钮会立即执行，因此应在点击前确认目标硬件安全。

建议：电机、功率电源等设备首次验证 OpenOCD 配置时，先关闭功率输出或断开执行机构。

### 3. Windows 下 OpenOCD 与 SEGGER J-Link 驱动不兼容

OpenOCD 的 J-Link adapter 通过 libusb 访问设备，J-Link 原生后端使用 SEGGER 官方 DLL 和驱动。Windows 下探针绑定官方驱动时，OpenOCD 可能报告 `LIBUSB_ERROR_NOT_SUPPORTED` 和 `No J-Link device found`。

这属于驱动体系差异，不是 target cfg 错误。使用 J-Link 时建议选择“J-Link 原生内核驱动”；OpenOCD 优先搭配 ST-Link 或 DAPLink/CMSIS-DAP。不建议用 Zadig 替换 J-Link 官方驱动，否则可能导致 J-Link Commander 和原生后端失效。

### 4. 被编译器优化掉的变量无法读取

文件内 `static` 全局变量可以读取，前提是变量仍存在于 ELF 符号表或 DWARF 中，并且具有稳定内存地址。Release/LTO 可能删除未使用变量、执行常量折叠，或只把值保存在寄存器中；这种情况下任何基于地址的变量工具都无法持续读取。

建议：用于观测的状态量使用明确宽度的类型，必要时加 `volatile`，同时避免为了调试在高速中断中加入复杂逻辑。

### 5. 设置采样率不等于实际采样率

界面中的频率是目标采样间隔。实际速率受探针性能、SWD 时钟、USB 延迟、后端类型、变量数量、变量宽度以及地址是否连续影响，不能保证所有组合都达到 8 kHz。

当前实现会合并可合并的内存读取，并批量向 GUI 投递数据，但界面暂未直接显示长期平均实际采样率和失败次数。这是后续最值得补充的可观测性功能之一。

### 6. 少数非关键界面异常会被静默忽略

绘图刷新、窗口退出和部分 UI 清理代码为了避免单次异常导致整个调试会话退出，仍有少量宽泛异常捕获。优点是界面更耐用，缺点是偶发问题可能缺少诊断信息。

建议后续增加有大小上限的本地滚动日志，只记录异常摘要和后端状态，不在正常界面堆叠日志窗口。

### 7. OpenOCD 实机覆盖仍少于 J-Link

J-Link 原生后端已经实际连接和读取验证；OpenOCD 的路径、cfg、端口、进程、TCL 协议、读取解码和失败分支已有自动化校验，但不同 ST-Link/DAPLink、不同芯片和不同 cfg 的组合仍需要实机矩阵验证。

建议优先覆盖：STM32F1 + ST-Link、STM32F4 + ST-Link、STM32H7 + ST-Link，以及一个 CMSIS-DAP 目标；每组至少进行连接、持续读取、断线重连和安全退出测试。

### 8. 数据库属于本机运行状态

`live_watch_history.db` 保存 ELF 路径、探针路径、监视变量和布局。它已从 Git 中移除并加入忽略，发布 EXE 时可以不附带，让程序首次运行自动创建。需要迁移已有配置时，应把数据库与目标 EXE 放在同一目录。

## 已解决的历史问题

| 历史问题 | 当前处理 |
| --- | --- |
| OpenOCD 启动失败但界面不知道原因 | 捕获日志、监测退出码、等待 TCL 就绪并显示日志尾部 |
| 固定端口误连旧 OpenOCD 实例 | 启动前检测占用，连接后用 `version` 校验身份，只绑定本机回环地址 |
| GDB/Telnet 暴露无用端口 | 默认禁用 GDB 和 Telnet，只启用 TCL 6666 |
| TCL 响应分包或无限增长 | 支持分片重组，并设置 1 MiB 响应上限 |
| OpenOCD 多通道结果错位 | 校验地址行、行数、word 数和 byte 数，异常时断开而非静默错配 |
| J-Link 与 OpenOCD 解码结果不一致 | 两个后端共用小端、位宽、有符号数和浮点解码函数 |
| packed/非对齐变量读取错误 | 跨 word 变量自动使用逐字节读取后按小端还原 |
| J-Link DLL 位数不确定 | 只加载所选目录中与当前进程位数匹配的 DLL |
| J-Link 烧录设备名被错误改写 | Commander 始终使用用户选择的原始设备名 |
| J-Link 多线程并发访问 | 采样、表格读写、写入和关闭共享同一互斥锁 |
| 表格硬件读取阻塞界面 | 可见变量由独立低速读取线程刷新，同一时刻只运行一个读取批次 |
| 断线重连冻结界面 | OpenOCD 启停与 J-Link 重新连接均放入后台线程 |
| ELF 烧录脚本路径注入 | 拒绝包含双引号或换行符的 ELF 路径 |
| OpenOCD 无法烧录 ELF | 使用专用线程执行 program、verify、reset，并在完成后恢复调试后端 |
| 烧录结果依赖弹窗 | 底部进度条显示 PROGRAMMING、DOWNLOAD OK 或 DOWNLOAD FAILED |
| 多套 Qt 导致打包失败或运行异常 | 打包固定 PyQt6，排除其他 Qt 绑定，构建后自动审计 |
| 大型 ELF 搜索卡顿 | 150 ms 防抖，单次最多渲染 2000 行，完整符号仍可检索 |
| 大结构体写数据库很慢 | 使用单事务批量保存和变量缓存 |
| 监视变量过多占满探针带宽 | 低速表格只刷新当前或悬浮窗口中展开且可见的标量 |
| 长时间波形导致内存持续增长 | 每通道历史缓存超过 40000 点后回收至最近 25000 点 |
| 高频采样导致 Qt 事件队列堆积 | 后台按时间批量发送采样数据 |
| 高频波形绘制卡顿 | 每条曲线限制显示点数并采用峰值保留降采样，完整缓存不受影响 |
| 采样数据无法带走 | 可选择已绑定变量，将当前缓存快照导出为 UTF-8 CSV |
| 悬浮后页面空白、标签仍占位 | 悬浮时移除标签并显示完整变量树，关闭后按逻辑槽位恢复 |
| ELF 变量只能加入当前窗口 | 双击加入当前窗口，右键可指定三个窗口，包括悬浮窗口 |
| 仓库携带 1.1 GiB 无用交叉编译链 | 已移除 ARM GCC；ELF/DWARF 改由 `pyelftools` 独立解析 |
| 本机数据库进入开源仓库 | 数据库已取消跟踪并加入 `.gitignore` |

以上解决项由 `python .\tools\validate_project.py` 覆盖其中可自动验证的部分。硬件相关行为仍以真实目标板测试为最终依据。
