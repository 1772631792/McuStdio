# 已知问题

## 1. OpenOCD target 脚本覆盖范围

当前内置 OpenOCD 包提供常见 STM32 target，但不包含 PY32/N32 等所有国产 MCU 的厂商脚本。这些芯片不能直接假定与 STM32 target 完全兼容。

当前防护：选择 `openocd.exe` 后，界面扫描其 `scripts/interface` 和 `scripts/target` 目录，只把实际存在的常用探针与 STM32 F1/F2/F3/F4/H7 项加入下拉框；全部其他配置通过右侧浏览按钮选择。进入工作站前还会解析并验证两个文件确实存在。不支持的芯片必须手动选择厂商提供的 cfg。

当前仓库实测可发现 `interface/jlink.cfg`，但内置 target 脚本中没有 PY32 配置。J-Link 后端读取正常并不能证明 OpenOCD 的 PY32 target 初始化、复位和 Flash 配置正确；在取得厂商 cfg 前，不应用 STM32 cfg 冒充 PY32 cfg。

剩余风险：文件存在不代表其寄存器、Flash 和复位配置一定与实际芯片匹配，仍需用户核对芯片型号。

## 2. OpenOCD 启动错误不可见

状态：已修复。

当前实现会捕获启动日志、监测子进程退出，并等待 TCL 服务就绪；失败时显示退出码和日志尾部，不再用固定睡眠假定启动成功。

## 3. 固定端口可能连到错误实例

状态：已修复。

当前只在回环地址启用 TCL 6666，GDB/Telnet 服务默认关闭。启动前检测端口占用，连接后发送 `version` 并校验响应；端口被占用时直接拒绝启动，不会连接旧实例。

## 4. OpenOCD 高速多通道读取边界

状态：已修复。

当前只解析带地址前缀的内存结果行，并严格校验返回行数、word 数和 byte 数；异常响应会断开并限速重连，不再静默错配通道。

J-Link 与 OpenOCD 后端共用同一个标量解码函数（小端序、位宽、有符号数和 IEEE-754 浮点）；差异只在原始内存数据的传输与文本解析。全项目校验包含 `g_cnt_val` 风格 float 与计数器的 OpenOCD 模拟响应测试。

## 5. packed 非对齐变量读取

状态：已修复。跨越 32 位 word 的变量不会进入块读取，会自动改用逐字节读取后按小端序还原。

## 6. OpenOCD 不能绝对保证不复位

OpenOCD 启动时会执行 target 初始化。是否触发复位取决于 target cfg、调试器、运输方式和接线。

建议：在电机、功率电源等高风险设备上使用前，先在低风险板卡上验证。

当前防护：启动 OpenOCD 前会弹出明确确认；普通 J-Link 连接和采样不会主动复位，只有用户确认的“复位”和“烧录”操作会发送复位命令。

## 7. J-Link DLL 位数与并发访问

状态：已修复。

- 只加载用户所选目录中与当前 Python/EXE 位数一致的 DLL，不再回退到另一位数或系统中的其他 J-Link 安装。
- 烧录始终向 Commander 传递原始设备名。
- 采样、表格读写、手动写入和句柄关闭共享同一互斥锁，避免多个线程同时调用同一原生 J-Link 句柄。
- ELF 路径进入 CommanderScript 前拒绝双引号和换行符，避免脚本命令被路径内容改变。

## 8. Qt 打包冲突

开发环境中如果同时安装 PyQt6、PySide6 或 PyQt5，pyqtgraph/PyInstaller 钩子可能尝试收集多套 Qt，导致打包失败、DLL 冲突或 EXE 启动异常。

当前防护：

- 仅保留 `packaging/Mcu_Studio.spec` 作为发布入口。
- 设置 `PYQTGRAPH_QT_LIB=PyQt6` 和 `QT_API=pyqt6`。
- 在 Analysis 中排除 PySide6/shiboken6、PyQt5、PySide2/shiboken2。
- 排除 pyqtgraph 可选导入的 matplotlib 和 scipy。

打包时只使用：

```powershell
python .\build.py
```

`build.py` 会在打包后检查 EXE 归档，发现第二套 Qt 时直接报错。不要使用 `doc/archive/packaging/` 中的历史 spec。

## 9. 大型 ELF、监视变量过多与长期运行

状态：已加固。

- ELF 变量浏览器对输入搜索做 150 ms 防抖，单次最多创建 2000 个界面行；完整符号仍保留在内存中，可继续通过关键字检索。
- 大型结构体/数组写入监视数据库时使用单事务批量保存，并缓存查询结果，避免逐成员提交和重复 SQL 查询。
- 低速监视只读取当前标签页中展开且实际显示在视口内的标量；折叠、屏幕外和其他标签页不持续占用调试器带宽。
- OpenOCD 标量字节读取合并为一条 `mdb address count`，不再每字节进行一次 TCL 往返。
- 最高采样率下，后台线程按约 25 ms 批量向 GUI 发送数据，避免每 20 个样本产生一次事件而造成事件队列持续增长。
- 每通道历史缓存超过 40000 点后回收至最近 25000 点，内存不会随运行时间无限增长。

仍需注意：界面中的 8 kHz 是目标采样间隔，不代表所有探针、USB 链路和变量地址布局都能达到 8 kHz。实际速率取决于探针、SWD 时钟、变量数量和地址是否连续。

## 10. Windows 下 OpenOCD 无法打开使用 SEGGER 驱动的 J-Link

现象：OpenOCD 日志出现 `LIBUSB_ERROR_NOT_SUPPORTED`，随后报告 `No J-Link device found`。

原因：原生 J-Link 后端使用 SEGGER DLL/官方 Windows 驱动；OpenOCD 的 J-Link adapter 使用 libusb。探针绑定 SEGGER 官方驱动时，OpenOCD/libusb 不能直接打开它。这发生在探针层，与 target cfg 无关。

建议：使用 J-Link 时选择程序的“J-Link 原生内核驱动”；需要 OpenOCD 时优先使用 DAPLink/CMSIS-DAP 或 ST-Link。不建议用 Zadig 替换 J-Link 驱动，否则可能导致 SEGGER DLL、J-Link Commander 和原生后端失效。界面现在会在 Windows 下提前显示该限制，并把对应启动错误翻译成明确建议。

## 11. 文件内 static 全局变量

文件内 `static` 全局变量可以读取，前提是变量没有被编译器优化删除，并且 ELF 的符号表或 DWARF 中仍保留它。Release/LTO 构建可能把未使用变量删除、常量折叠或仅保存在寄存器中，此时任何基于 ELF 地址的在线观测工具都无法持续读取它。

不同源文件可以存在同名 `static` 变量。程序会为冲突项生成可区分的内部名称；重新编译 ELF 后应让应用自动重新提取，或在 ELF 变量浏览器中点击“重新提取当前 ELF”。

## 12. 三个调试窗口与悬浮行为

当前固定保留三个调试窗口，不再支持动态新增、删除或任意拖拽吸附。双击标签会把对应页变成独立悬浮窗口，关闭悬浮窗口后恢复到原标签。这种固定槽位设计用于保证数据库中保存的变量不会因窗口顺序改变而串页。

## 13. 数据库包含本机状态

`live_watch_history.db` 保存 ELF 路径、工具链路径、监视变量和布局，属于本机运行数据。公开发布源码时不应提交个人最新数据库内容；分发 EXE 时可不附带数据库，让程序首次运行自动生成。若需要迁移配置，应把数据库与目标 EXE 放在同一目录。
